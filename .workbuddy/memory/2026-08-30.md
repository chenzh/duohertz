## 踩坑 / 硬知识

- **推理栈通常已在跑**：Gateway :8080、ACE worker :8101、SA3 worker :8102。
  起服务前先 `curl /v1/health/inference`，确认 `sa3_mlx: ok` 再跑批，别重复启动（EADDRINUSE）。
  注意 worker 端口是 8101/8102，不是 PRD 里写的 8001/8002。
- **macOS 自带 bash 3.2 没有 `mapfile`**，用 `while IFS= read -r` 代替。
- **`beatscape-cover.py` 的参数是 `--all`**，不是 `--all-catalog`。
- **首音偏晚**：母带有长静音 intro 时首音会落到 2.6–13.7s。
  用 specs 里的 `clip_t0` 逐首设切片起点（= 首个强 onset − 1.5s），改完要重跑 clip → ingest → chartgen（ingest 会把 bpm 重置回 specs 值，正好重置检测缓存）。
- **BPM 八度误判**：onset 密度估计会把 8 分音符当分拍（90 BPM 报 188）。
  已在 `beatscape-audio.py` 加 `_fold_octave()` 修复。chartgen 会把检测值写回 catalog，
  所以修 bpm 必须先 ingest 重置 hint 再 chartgen。
- **ingest 会整条替换 catalog entry**，会丢 `stream_audio`，所以 ingest 之后必须再跑 `ingest-stream`。
- **验证真推理 vs synth fallback**：synth 是单声道 110/165/220Hz 正弦；真推理为立体声、频谱宽。
  批量校验看 `channels == 2` + rms + 频谱质心即可。
- SA3 small 180s 母带约 5s/首（13.5× 实时），峰值 RAM 1.7 GB —— 跑批成本极低，
  不必为了省时间用 synth 或短时长。

### 下载卡死根因 + 最终解法（重要，下次直接照做）

- **真凶不是带宽，是并发 `ollama pull` 把断点文件写坏了**：两个 pull 同时拉同一模型 → blobs 里的 `*-partial` 和 `*-partial-0..N` 被多写者踩乱 → 之后每次 `pull` 在已完成的 blob 之后请求主分片时**秒断 `Error: EOF`**（看似卡住，实连都没连上）。单发也 EOF 是因为 resume 状态已损坏。
- **判定法**：若 `ollama pull` 在第一个 100% 的 blob 之后立刻 `Error: EOF` 且 `du` 不涨 → 就是 partial 损坏。
- **解法**：`rm -f ~/.ollama/models/blobs/sha256-<大partial>*-partial*` 清掉损坏大分片（保留已完整的 931MB 小 blob），然后**只跑单进程** `ollama pull qwen3.8:27b-mtp-q4_K_M`，立刻恢复（实测 2–6 MB/s，65 分钟拉完 17GB）。
- **沙箱每 ~10 分钟会回收后台 pull 进程**（disown/nohup 也活不过约 9 分钟）。所以无人值守下载要用**自修复监控循环**：每 60s 查 `pgrep -f "ollama pull"`，死了就 `nohup ollama pull ... & disown` 重启；partial 在磁盘上，重拉自动续传、进度不丢。截止 11:21 已用此法把 `qwen3.8:27b-mtp-q4_K_M` 拉完（17GB，列表已就绪）。
- **实测性能**：M5 Pro 48GB，27B Q4 + MTP 投机解码 → 生成 **18.7 tok/s**（229 tok / 12.2s），prompt 预填充 ~37 tok/s。比堆到 Q8 划算（Q8 吃 60% 内存、速度砍半）。
- 用户本机 Terminal 的 `ollama` 在 PATH（brew 装 `/Users/zhenhuachen/.homebrew/bin/ollama`），Ollama.app 也已装（0.33.2，菜单栏托管服务，最稳）。
- **最终决定（10:27）**：只保留 `qwen3.8:27b-mtp-q4_K_M`（q4 本地 `ollama run` 已跑通，日常用），**放弃下载 q8_0**。已取消 q8 后台 pull 并删除其 793MB 残留 partial，磁盘回到 ~370Gi 可用。如后续要更高精度再单独拉 q8（27.9G，装得下）。

### 把本地 Ollama 模型接进 WorkBuddy（可复用 · 踩坑已查清）

- 配置文件：`~/.workbuddy/models.json`（JSON，`{models:[...]}`）。每条字段：`id` / `name` / `vendor` / `apiKey` / `url` / `supportsToolCall` / `supportsImages`。
- **关键**：自定义本地模型的 `id` **必须以 `custom-local:` 开头**（`CUSTOM_LOCAL_MODEL_PREFIX`，在 `app.asar.unpacked/cli/dist/codebuddy.js` 里），否则 WorkBuddy 不识别为自定义模型、不会走你的 URL。
- WorkBuddy 发请求时会用 `stripCustomLocalModelPrefix()` 把 `custom-local:` 前缀剥掉，剩下的部分作为 OpenAI 接口的 `model` 名。所以 `id: "custom-local:qwen27b"` → 实际发给 Ollama 的 `model` 是 `qwen27b`。
- `url` 填 `http://localhost:11434/v1` 即可（代码会自动补 `/chat/completions`）。
- Ollama tag 含特殊字符（如 `qwen3.8:27b-mtp-q4_K_M`），直接当 model 名在配置里不优雅 → 用 `ollama create qwen27b -f Modelfile`（FROM 原 tag）建一个干净别名，配置里用别名。
- apiKey 本地随便填（如 `ollama`），Ollama 不校验。
- 改完**重启 WorkBuddy** 才加载新模型；在模型选择器里选「本地 Qwen3.8-27B (Q4+MTP)」即可用本机算力（数据不出机器）。
- 验证链路：`curl http://localhost:11434/v1/chat/completions -d '{"model":"qwen27b",...}'` 应返回 200。注意 Qwen3.8 会先出 reasoning 段，短 max_tokens 时 content 可能为空，属正常。

## 角色三视图（追加）

新增 `scripts/beatscape-character-views.py`：7 个 District 角色 ×（正面/侧面/背面）三视图，统一基线对齐。

**核心踩坑**：用 `_raster(ops, w, h, ox, scale)` 合成多面板时，**ox 必须只在该面板内做居中**（panel 内 art 0..w → out 0..w），panel 在 sheet 中的 x 位置由 `sheet[:, x0:x0+w] = art` 的赋值决定。如果误写成 `ox = x0 + (w/2 - 256*scale)`，会把画布原点推到负值，整张图都画到画布外。调试时用 `accent_match.sum()` 像素统计可以秒定位这种 bug。

**三视图每个角度必须把道具画完**：头戴耳机（正=2 cup / 侧=1 cup / 背=2 cup 但窄）、围巾（前拖/侧甩/背下）、工具带（前/侧/绕/背）、胸口菱形（正面）/ 背后印（背面）。任何角度缺了道具都会破坏 IP 的"可衍生性"。

### 关键硬知识（CLIP 77-token 截断）

Animagine/SDXL 的两个 text encoder 都是 **77 个 BPE 子词**上限，**不是 77 个逗号 tag**。
原 prompt ~34 个 tag 整串 tokenize 后膨胀到 ~89–112 BPE → 尾部（共振菱形 halo 之后的胸口徽记 / 背景 / 质量标签）被静默截断。
修复：`fit_clip()` 用 `pipe.tokenizer` 对**整串**测真实 BPE，保头部（subject+rating+共振菱形 MOTIF）和尾部（quality），从中间从后往前丢冗余 tag。
已验证 7 角色 × 3 视角共 21 条全部 ≤77 BPE 且 motif+quality 保住。
→ 教训：估 CLIP 长度必须用 tokenizer 测整串，绝不能用逗号 tag 数近似。

## 14:43 修复：dev server 陈导致角色图标全不显示
- 现象：网站界面 7 张角色头像全破（Home 条 / Library 卡 / Characters 页 / PlayField 水印都不出）。
- 根因：占用 5175 的 dev server 是**上次会话留下的陈旧实例**，在 `public/characters/` 子目录创建之前就启动了。vite 6 dev 在 `base:/beatscape/` 下 public 静态服务对请求 `/beatscape/characters/<slug>.png` 找不到文件 → 返回 SPA 兜底 `index.html`（HTTP 200 + text/html，浏览器当破图）。对比：`/beatscape/catalog.json`、`/beatscape/reports/audit-report.json` 正常（public 根/其他子目录文件 OK），唯独 `public/characters/` 取不到 → 锁定是"server 启动时该目录还不存在"的陈旧状态。
- 诊断命令：`curl -s -o /dev/null -w "%{http_code} %{content_type} %{size_download}" http://localhost:5175/beatscape/characters/pulse-core.png`（200 + text/html + 1747 = 兜底页；正常应 200 + image/png + 真实字节数）。
- 解法：kill 占用 5175 的旧 node 进程（lsof -i :5175 拿到 pid），用 Bash `run_in_background` 从 worktree 干净重启 `npm run dev`（普通 `nohup &` 在工具调用结束会被回收，必须用 run_in_background 常驻）。重启后 7 张图全部 200 image/png。
- ⚠️ 用户浏览器可能缓存了旧的破响应 → 需硬刷新（Cmd+Shift+R）才能看到图标。
- 经验：往 vite public/ 加**新子目录**后，若 dev server 是早前启动的，必须重启 dev server，否则新子目录静态资源取不到（返回 SPA 兜底页，不像普通 404 那么直观）。
